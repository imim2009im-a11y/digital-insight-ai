# أمر التطوير الهندسي الثاني — موثوقية التنفيذ السحابي

## المهمة

طوّر النواة الموجودة في مسودة #83، دون إنشاء مشروع أو منظومة مكررة.
اجعل نتيجة التحقق مرتبطة بالشيفرة وحالة Git وأدوات التشغيل، وسجّل
المحاولات المنقطعة والفاشلة، واحفظ دليلاً منظماً يمكن مراجعته.

## النطاق والتفويض

- العمل على `codex/ia-cloud-preflight` فقط؛ لا دمج أو نشر إنتاجي.
- لا أسرار أو موارد مدفوعة أو DNS أو صلاحيات إضافية أو جهاز محلي.
- افحص موارد البيئة السحابية قبل ادعاء وجود مشكلة أداء.
- استخدم البحث الرسمي للتحقق من خيارات حفظ الأدلة والتكلفة.

## التنفيذ

1. افحص مسودة #83 والشيفرة والحوكمة وحالة الموارد.
2. أضف بصمة لإصدارات ومسارات Git وNode وBash وPython إلى مفتاح الاستئناف.
3. حوّل السجلات المتروكة بحالة running إلى interrupted عند امتلاك القفل.
4. احفظ أخطاء بدء العملية بحالة error، دون نص الاستثناء أو الأسرار.
5. صدّر تقرير JSON ذرّياً بقائمة حقول محدودة داخل بيانات Git.
6. شغّل النواة في CI القائم وأضف دليلها إلى ملخص التنفيذ، دون تخزين artifacts جديد.
7. اختبر تغير runtime، واستعادة المقاطعة، والخطأ، والتصدير؛ ثم الفحوص القائمة.
8. أجرِ مراجعة مستقلة، ثم حدّث المسودة نفسها وتحقق من CI البعيد.

## معايير القبول

نجاح الاختبارات مع بقاء الموقع كما هو. منع إعادة استخدام نجاح قديم عند
تغير بصمة runtime. لا اعتبار لمحاولة منقطعة كنجاح. وجود حالة ودليل تشغيل
قابلين للفحص. لا إعلان عن استئناف عبر جلسات متعددة أو تشغيل مستمر دون اختبارهما.

## حدود التصميم والتراجع

الدليل المحفوظ في ملخص GitHub Actions يبقى وفق سياسة احتفاظ الخدمة؛ ليس
نسخة SQLite قابلة للاستيراد. لم يُبنَ استيراد لنجاحات خارجية لأنها تحتاج
سياسة ثقة تمنع تجاوز التحقق ببيانات حالة مزورة.

البيئة الحالية أظهرت نحو 9.7 GiB ذاكرة و30 GiB مساحة متاحة، دون دليل
على ضغط موارد. التحسين هنا لموثوقية التنفيذ، لا ادعاء تسريع الجهاز أو
تغيير موارد منصة Work التي لا تتيح هذه المهمة التحكم بها.

التراجع: إغلاق المسودة، أو revert للالتزام المراجع إذا دُمج لاحقاً.

فُضّل ملخص CI على artifacts جديدة لأن حصة تخزين الحساب وفوترته غير
متحققتين. لا تشغيل دوري جديد؛ يجب أولاً التحقق من المصادقة والحفظ الدائم
ومن سقف التكلفة والتكرار والتنبيهات في دورة مستقلة.
